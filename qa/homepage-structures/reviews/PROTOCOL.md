# Structural diversity gate

Review scope:20 independent grayscale wireframes; before full color/art implementation. The previous theme/color-oriented gate was too permissive. This gate is about the page's geometry, entry point and functional behavior, including phone adaptation. A shape name is not proof.

Inspect the real complete active documents and native desktop/phone viewport images, plus at least two substantive working states per study. Exercise actual navigation with pointer and keyboard where the model changes views; do not infer working interaction from a screenshot. No need to read author self-justification before the first pixel judgment. After first observations, consult the content map for hidden inventory and note missing/abridged facts. Palette, font family, image mood, cultural name or agent identity cannot establish structural difference.

For every assigned pair record one of:

- D: defensibly different architecture/behavior. Cite concrete geometry and navigation distinctions in both desktop and phone.
- R: related family but meaningful structural differences. State the shared structure and the substantive difference; not merely colors/labels/section order.
- N: near duplicate or same underlying architecture. Require one explicit structural rework before either advances; do not pass on theme alone.
- U: uninspected/uncertain; record exactly what could not be verified. U is not acceptance.

Axes to compare: dominant spatial geometry; landing task/entry; persistent vs replaced context; navigation and information reveal model; relationship between sections/views; phone transformation; how whole information remains reachable. Repeated hero+outlined-panels sequence, same rail+reader with new metaphor, or same stacked cards with new edges is N. Two layouts that both use HTML rectangles can still be different (a semantic ledger vs filmstrip); the question is actual architecture and behavior, not a polygon count.

If an unusual overview drops needed info or sends everything to one generic dashboard drawer, flag it. If phone uniformly becomes the same stack despite desktop variety, flag it. Distinguish structural rejection from fixable clipping/contrast/focus defect. No automatic all-pass, no statistical claim from pair counts, no favorite/shortlist selection in this gate. Preserve first versions; reworks are separate. Accepted structure is not final user approval or production authorization.

Return assigned pair JSON with idA/idB/verdict/reason and a human review naming inspected files/live states, rejected pairs and exact required changes, accessibility/interaction defects and limitations. Each reviewer is fresh-context and did not author these20. Parent must inspect actual structures before final delivery. Final implementation gets a fresh pairwise audit after art/motion too.
